\begin{abstract}
Evaluating scheduling policies and system configurations for Large Language Model (LLM) serving requires expensive GPU clusters, limiting accessibility for systems researchers. We present \sysname{}, a lightweight emulation framework that hooks into vLLM---a production LLM serving system---to replace GPU computation with profile-driven latency predictions. Unlike discrete-event simulators that reimplement scheduling logic, \sysname{} runs the \emph{real} vLLM engine with unmodified request processing, scheduling, and KV cache management, replacing only the GPU forward pass with calibrated timer-based delays. This native integration preserves forward compatibility as vLLM evolves and ensures identical API and scheduling behavior. We evaluate \sysname{} on multiple GPU configurations (RTX 3060 to A100$\times$4) and model sizes from 3B to 72B parameters across online serving and offline batch inference. Our results show \todo{X\%} mean TPOT error and \todo{X\%} mean E2E latency error under production workload traces. We further demonstrate CPU-only emulation on commodity hardware using the same GPU-build binary, enabling cluster-scale evaluation without GPU access beyond a one-time profiling pass. We identify an inherent tension between hook-based emulation and async scheduling pipelining that manifests as TTFT underestimation at high load---a systems insight relevant to any emulation approach that preserves real scheduler semantics.
\end{abstract}

\section{Introduction}
% ============================================================

The rapid growth of Large Language Model (LLM) deployment has driven significant innovation in serving systems~\cite{kwon2023vllm, yu2022orca, zheng2024sglang}. Modern LLM serving involves complex scheduling decisions---chunked prefill, continuous batching, KV cache management, prefill/decode disaggregation---that critically impact latency, throughput, and cost. Evaluating these decisions requires running the full serving stack under realistic workloads on GPU hardware.

However, GPU access remains a bottleneck for systems research. A single evaluation run (profiling + benchmarking across multiple rates) can consume hours of GPU time. Researchers iterating on scheduling algorithms, memory management policies, or cluster-level orchestration strategies face a costly feedback loop: each design change requires re-running the full GPU evaluation.

\textbf{Existing approaches occupy different design points.} Discrete-event simulators such as Vidur~\cite{agrawal2024vidur} reimplement scheduling logic and request flow in a separate environment. This is useful for broad capacity planning and what-if simulation, but requires parallel maintenance as the serving engine evolves. Hardware emulators like REVATI~\cite{agrawal2024revati} target deeper GPU-level emulation by intercepting CUDA kernels with calibrated delays, but require tight integration with the CUDA runtime and are more infrastructure-coupled.

\textbf{Our approach: hook-based emulation.} We observe that LLM serving systems have a clean separation between \emph{scheduling} (CPU) and \emph{computation} (GPU). The scheduling layer---request queuing, batch formation, memory allocation, output processing---runs on CPU and determines system behavior. The GPU only executes the forward pass, whose latency is a deterministic function of batch composition (total tokens, prefill vs.\ decode ratio).

\sysname{} exploits this separation by hooking into vLLM at the executor level---the interface between scheduler and GPU worker. When a batch is scheduled, instead of dispatching to the GPU, \sysname{} looks up the predicted latency from a pre-collected profile and returns a timer-based \texttt{Future} that resolves after the profiled delay. The real vLLM scheduler, memory manager, tokenizer, and API server all run unmodified. Only the GPU forward pass is replaced.

We structure our contributions as follows:

\textbf{Core contribution.} \sysname{} is a native vLLM emulation substrate that requires no separate simulator stack. The entire integration consists of a lightweight executor hook---approximately \todo{X} lines of pure Python---that intercepts at the boundary between scheduler and GPU worker. All other vLLM components run unmodified, including the KV cache manager, block allocator, prefix caching, eviction policies, and OpenAI-compatible API server. Switching between real GPU and emulation is a single environment variable.

\textbf{Methodology contribution.} \sysname{} provides a practical profiling and calibration workflow using native vLLM execution paths. A one-time profiling pass under representative load conditions produces a compact profile ($\sim$27KB) that drives all emulation. No separate profiling infrastructure, no CUDA dependency at runtime, no manual parameter tuning. Online serving and offline batch inference both work through the standard vLLM entrypoints and benchmarking tools.

\textbf{Systems insight.} We identify an inherent tension between hook-based emulation and vLLM's async scheduling pipelining: pending result handles serve dual roles as both scheduling correctness tokens and timing signals. This coupling causes TTFT underestimation at high load---a finding relevant to any emulation approach that preserves real scheduler semantics. We analyze this trade-off and show that steady-state metrics (TPOT, throughput, E2E) are robust to the pipelining mismatch while transient metrics (TTFT) are sensitive to it.

\textbf{Breadth and extensibility.} By combining the executor hook with lightweight CUDA stub libraries and a synthetic worker, \sysname{} runs the \emph{same GPU-build binary} on CPU-only hosts. This enables cluster-scale evaluation with tens of emulated instances on commodity hardware, tensor-parallel serving, and prefill/decode disaggregation---all preserving real vLLM scheduling behavior. As vLLM adds features (speculative decoding, multi-step scheduling), \sysname{} automatically supports them with no code changes.

We evaluate \sysname{} on multiple GPU configurations (RTX 3060 to A100$\times$4) and models from 3B to 72B parameters under production workload traces (ShareGPT~\cite{sharegpt2023}, BurstGPT~\cite{wang2024burstgpt}). For online serving, we observe \todo{X\%} mean TPOT error and \todo{X\%} mean E2E error across request rates 1--8. For offline batch inference via \texttt{LLM()}, throughput error is within \todo{X\%}. We further demonstrate tensor-parallel serving (TP=4), prefill/decode disaggregation, and CPU-only cluster-level evaluation on commodity CloudLab servers.

\section{Background and Motivation}
% ============================================================

\subsection{LLM Serving Architecture}

Modern LLM serving systems process requests through an iterative decode loop. Each \emph{step} runs a forward pass over all active tokens---both new prefill tokens from incoming requests and decode tokens from ongoing generation. The output is one new token per active request.

vLLM~\cite{kwon2023vllm} introduced \emph{PagedAttention} for efficient KV cache management and \emph{continuous batching} (inspired by Orca~\cite{yu2022orca}) where new requests join the batch dynamically. vLLM v1 (v0.18+) adds:

\begin{itemize}
\item \textbf{Chunked prefill:} Long prompts are split across multiple steps, interleaved with decode tokens from other requests.
\item \textbf{Async scheduling:} The scheduler prepares the next batch while the GPU executes the current one (\texttt{batch\_queue\_size=2}).
\item \textbf{CUDA graph compilation:} Forward passes are compiled into CUDA graphs at startup for each batch size, eliminating kernel launch overhead.
\end{itemize}

\subsection{The Cost of GPU-Based Evaluation}

Evaluating a scheduling policy change requires:
(1) starting the serving system,
(2) warming up CUDA graphs and GPU thermal state,
(3) running benchmark workloads at multiple request rates,
(4) collecting per-request latency metrics.
On a single GPU, this takes 30--60 minutes per configuration. Researchers iterating on policies need many such runs, making GPU time the primary bottleneck.

\subsection{Why Simulation Falls Short}

Discrete-event simulators~\cite{agrawal2024vidur} reimplement the serving logic in a simplified model. This creates two problems:

\textbf{Fidelity gap.} The simulator's scheduling decisions may diverge from the real engine, especially for edge cases in chunked prefill, preemption, and prefix caching.

\textbf{Maintenance burden.} vLLM evolves rapidly (monthly releases). Each release changes scheduling internals, requiring simulator updates to stay accurate.

\subsection{Emulation: Running the Real Engine}

Instead of reimplementing the system, we \emph{emulate} it: run the real vLLM engine but replace GPU computation with profiled delays. This preserves all scheduling behavior while eliminating GPU dependence. The key insight is that GPU forward pass latency is a \emph{deterministic function} of batch composition that can be profiled once and replayed.

The system has three components: (1) an \emph{executor hook} that replaces GPU computation with timed delays, (2) a \emph{cost oracle} that predicts forward pass latency from batch composition, and (3) an \emph{emulator worker} that enables CPU-only operation by providing synthetic hardware metadata.

\subsection{Executor Hook: Replacing GPU with Timed Delays}
\label{sec:hook}

The executor hook intercepts the serving engine's dispatch to the GPU worker. For each scheduled batch, it queries the cost oracle for the predicted latency and returns a delayed response that resolves after the profiled time. The intervention requires modifying only two lines in the executor's dispatch path.

\textbf{Preserving async scheduling semantics.} Modern serving engines use \emph{asynchronous scheduling}: while the GPU executes batch $N$, the scheduler prepares batch $N{+}1$ in parallel. This pipelining is critical for throughput. Naively replacing GPU execution with a blocking delay breaks this contract---the scheduler expects the GPU dispatch to return immediately with a pending result handle, not to block the engine thread.

We discovered that the async scheduler tracks in-flight batches through pending result handles. When all handles resolve before the next scheduling round, the scheduler computes zero new tokens for every request, causing a deadlock. On real GPU hardware, the result handle remains pending because GPU execution is dispatched to a background thread. Our emulator must replicate this behavior.

\sysname{} uses timer-based pending handles that resolve after the profiled delay, mimicking the real GPU's asynchronous execution model. This preserves the scheduler's pipelining invariant while accurately modeling GPU timing.

\textbf{Virtual GPU timeline.} To model the GPU as a serial resource, timer delays are chained: each step begins only after the previous step completes. This prevents artificial parallelism that would occur if timers ran independently.

\textbf{Scheduling compensation.} The timer approach introduces a subtle pipelining advantage: the engine can accept and schedule new requests during the simulated GPU step, whereas on real GPU the engine thread is blocked during execution. New requests arriving mid-step must wait on real hardware but are served immediately in emulation. We compensate by adding a profile-derived scheduling delay (half the average decode step duration) to batches containing new requests when prior GPU work is still in flight.

\textbf{Timing modes.} \sysname{} supports \emph{realtime} mode (wall-clock delays for accurate latency measurement) and \emph{accelerated} mode (no delays, for rapid policy exploration where only relative ordering matters).

\subsection{Cost Oracle: Profile-Driven Latency Prediction}
\label{sec:oracle}

The cost oracle maps batch composition to forward pass latency. The primary input is \emph{total scheduled tokens}---the sum of all prefill and decode tokens in a batch. We observe that forward pass latency is predominantly determined by this single quantity, as modern serving engines process all tokens in a unified batch regardless of their type.

However, online serving and offline batch inference exhibit different latency characteristics at the same token count due to differences in CUDA graph utilization, memory access patterns, and scheduling overhead. The oracle maintains separate latency profiles for each context, selected automatically based on the execution path.

Latency is predicted via linear interpolation between profiled data points, with power-law extrapolation ($L(t) = a \cdot t^b$) beyond the profiled range.

\subsection{CPU-Only Operation}
\label{sec:worker}

A key goal of \sysname{} is enabling GPU-free evaluation on commodity hardware. This requires running the \emph{GPU build} of the serving engine (to preserve identical code paths) on a CPU-only host.

We achieve this through three mechanisms: (1) a \emph{platform plugin} that registers as a GPU-compatible platform, providing synthetic device capabilities and memory information; (2) \emph{stub libraries} that satisfy native code dependencies without actual GPU runtime; and (3) a \emph{lightweight worker} that provides hardware metadata (KV cache layout, available memory) derived from the model configuration, without loading model weights or initializing GPU devices.

The executor hook intercepts all computation dispatches, so the worker's compute methods are never invoked. The scheduler operates normally using the synthetic metadata, making scheduling decisions identical to a real GPU deployment.

\textbf{Preserving KV cache semantics.} A critical advantage of running the real engine is that vLLM's KV cache management---block allocation, eviction, and automatic prefix caching---runs unmodified. The scheduler tracks cached blocks, reuses matching prefixes, and applies memory pressure (preemption, waiting queues) based on the emulated memory budget. This enables researchers to study KV cache policies, evaluate systems like LMCache, or modify eviction strategies, and observe realistic scheduling effects on CPU-only hosts---an capability that simulators must reimplement from scratch and analytical models cannot provide.

\subsection{Profiling}
\label{sec:profiling}

Profiling is a one-time process per GPU/model combination using standard vLLM execution paths and benchmarking tools---no separate profiling infrastructure is needed. The profiler instruments the serving engine to record per-step wall-clock timing along with batch metadata (token count, request composition). We collect traces under diverse load conditions---multiple request rates for online serving, multiple batch sizes for offline inference---after a warmup phase to reach thermal steady state. Profiling time scales with GPU and model size; for a single-GPU 14B model, profiling completes in under 30 minutes.

The profile builder aggregates per-step measurements, computes median latencies at each token count, and applies cross-reference outlier detection to remove CUDA graph compilation artifacts and cold-start anomalies. The resulting profile is a compact representation ($\sim$27KB) of the GPU's forward pass behavior across the relevant batch composition range.

\section{Limitations}
% ============================================================

\textbf{First-token latency.} TTFT error ranges from +3\% (R=1) to $-$12\% (R=8) on our development GPU (RTX 3060, Qwen-1.5B). The underestimation at high rates is caused by the emulator's engine loop running faster than real GPU---the hook skips 3ms of worker-side CPU preparation (attention metadata construction, input tensor building) per step. This compounds via a concurrency feedback loop: faster steps $\rightarrow$ lower steady-state concurrency $\rightarrow$ lower oracle predictions $\rightarrow$ even faster steps. We mitigate this with a worker prep surrogate that performs equivalent CPU work, but the remaining gap reflects the difficulty of exactly matching the real worker's CPU cost without running its GPU-dependent code paths. On larger models where GPU compute dominates ($>$50ms per step), this 3ms overhead is $<$6\% and the feedback loop is negligible.

\textbf{CUDA graph compilation.} First-encounter compilation of CUDA graph shapes (50--100ms per shape) contaminates both profiling data and real baselines. We mitigate this with a comprehensive warmup sweep that pre-compiles all padded capture sizes before profiling and benchmarking. Without this warmup, TTFT errors exceed 20\% due to asymmetric compilation between profiling and serving sessions.

\textbf{Async scheduling sensitivity.} vLLM V1's async scheduler (default since February 2025) pipelines batch scheduling with GPU execution via \texttt{batch\_queue\_size=2}. This creates a fundamental tension for emulation: the engine's pipelining behavior depends on when pending futures resolve, which is determined by our timer mechanism. Prior GPU-free emulation work~\cite{agrawal2024revati} predates this scheduler change and does not address this challenge.

\textbf{Thermal state sensitivity.} GPU thermal state affects forward pass latency by up to 2$\times$ on consumer GPUs (e.g., RTX 3060 boost vs.\ throttle). Profiles must be captured under representative thermal conditions. We mitigate this with a warmup phase, but profiling and benchmarking in different sessions may yield inconsistent results.

\textbf{Single-framework scope.} \sysname{} is currently implemented for vLLM v0.18.x. The hook-based approach is applicable to other frameworks (SGLang, TensorRT-LLM) with framework-specific executor hooks, but this is not yet implemented.

\textbf{Network and communication.} For multi-GPU configurations, we profile the end-to-end step cycle including communication overhead, but do not model network effects independently. Cluster-level emulation with separate hosts does not capture inter-node network contention.

\section{Discussion}
% ============================================================

\subsection{Emulation vs.\ Simulation}

\sysname{} occupies a distinct point in the fidelity--cost trade-off space. Simulators like Vidur reimplement scheduling and serving logic, which is useful for broad capacity planning but requires parallel maintenance and diverges from production behavior as the engine evolves. Hardware emulators like REVATI target deeper runtime transparency through CUDA-level interception, but are more infrastructure-coupled. \sysname{} explores a lightweight, native-vLLM design point: direct experimentation inside the real engine with a small integration surface, trading some transient-metric fidelity for easier adoption and forward compatibility.

\subsection{Async Scheduling and Emulation Fidelity}

Our experience reveals a fundamental tension in hook-based emulation of async serving engines. vLLM's async scheduler uses pending result handles both for scheduling correctness (tracking in-flight batches via \texttt{num\_output\_placeholders}) and for pipelining (preparing the next batch while the GPU executes). On real hardware, GPU dispatch returns immediately with a pending handle that resolves asynchronously. The emulator must replicate this timing to avoid deadlock, but any timer-based approach creates a pipelining window where the engine can admit new requests earlier than on real GPU. This manifests as TTFT underestimation that grows with load. We find that steady-state metrics (TPOT, throughput, E2E) are robust to this effect, while TTFT is sensitive---a distinction relevant to any emulation approach preserving real scheduler semantics.

\subsection{Profile Portability}

Profiles are specific to a GPU/model combination but independent of workload, request rate, and serving configuration. A single profile enables evaluation across unlimited scheduling policies, batch sizes, and rate patterns. We envision a community-maintained profile library for common GPU/model combinations, reducing the profiling barrier further.

\subsection{Cluster-Scale Implications}

By enabling CPU-only emulation, \sysname{} makes it practical to evaluate cluster-scale serving configurations (tens to hundreds of instances) on commodity hardware. Researchers can explore load balancing, model placement, and heterogeneity-aware scheduling without provisioning GPU clusters. Each emulated instance runs the full vLLM serving stack with profiled timing, preserving realistic per-instance behavior including queueing dynamics and memory pressure.

\section{Related Work}
% ============================================================

\textbf{LLM Serving Systems.} vLLM~\cite{kwon2023vllm} introduced PagedAttention and continuous batching. Orca~\cite{yu2022orca} pioneered iteration-level scheduling. Sarathi-Serve~\cite{agrawal2024sarathi} proposed chunked prefill to balance prefill/decode latency. Splitwise~\cite{patel2024splitwise} disaggregates prefill and decode across GPU pools. SGLang~\cite{zheng2024sglang} optimizes structured generation with RadixAttention. These systems all require GPU evaluation; \sysname{} enables exploring their scheduling design space without GPU.

\textbf{LLM Serving Simulation.} Vidur~\cite{agrawal2024vidur} is a discrete-event simulator that models LLM inference request flow, scheduling, and GPU execution. It is useful for capacity planning and broad what-if analysis, but reimplements scheduling logic and KV cache management in a separate environment, requiring parallel maintenance as the serving engine evolves. \sysname{} avoids this by running inside the real engine---including real KV cache management, real prefix caching, and real memory pressure handling---with no simulator-side reimplementation.

\textbf{Hardware Emulation.} REVATI~\cite{agrawal2024revati} takes a lower-level approach, intercepting CUDA kernels and replacing them with calibrated delays. This targets stronger framework transparency through deeper runtime interception, but requires tight integration with the CUDA runtime and specific kernel implementations. \sysname{} explores a different design point: operating at the executor level (not kernel level), which keeps the integration surface small and enables direct development inside native vLLM. The trade-off is that our approach is more sensitive to async scheduling timing (\S\ref{sec:hook}), while gaining easier adoption and forward compatibility.

The llm-d project~\cite{llmd2024sim} provides a vLLM-based inference simulator oriented toward API-level simulation and infrastructure testing. Our approach differs in targeting fidelity to per-request latency metrics (TTFT, TPOT) through a minimal hook-based design that requires only two lines of modification at the executor boundary, preserving the unmodified scheduler and engine loop.

\textbf{Offline Analysis Tools.} LLM profiling tools like DeepSpeed-FastGen~\cite{holmes2024deepspeed} provide performance analysis but not emulation. FlexGen~\cite{sheng2023flexgen} explores offloading strategies with analytical models. These complement \sysname{}'s profile-driven approach.
