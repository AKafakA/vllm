# GhostServe

Profile-driven online emulator for [vLLM](https://github.com/vllm-project/vllm).
GhostServe replaces vLLM's GPU forward pass with a latency draw from a
profile pack captured once on a real GPU. The scheduler, HTTP stack,
admission path, tokenizer, and output pipeline are vLLM's own unmodified
code; only the per-step latency is faked.

This repository accompanies the paper *GhostServe: Profile-Driven
Online Emulation of LLM Serving Systems* (anonymous submission). The
paper's six Table 1 cells are reproducible from this branch.

---

## What's in this repo

```
vllm/                          # patched vLLM 0.18.1 (one 62-line hook in
                               #   v1/worker/gpu_worker.py + plugin entry point
                               #   in pyproject.toml; everything else is upstream)
vllm_emulator/                 # plugin code (~1.7K lines Python)
  oracle/                        density-aware step-latency oracle (adaptive-K,
                                 two-distribution decode/prefill 2D table)
  hooks/executor_hook.py         intercepts execute_model(); returns a pending
                                 Future whose timer resolves after the predicted
                                 step latency
  profile/build_serving_profile_filtered.py
                                 builds the profile pack from per-step traces
  platform.py                    vLLM platform-plugin entry point
  cuda_mock.py                   torch.cuda stubs for CPU-only hosts (optional)
tools/                         # 14 reproduce-the-paper scripts (see below)
```

This release is **code only** — no bench data, no profile packs, no
captured traces. Everything in the paper is reproducible from this tree
via the documented commands below.

## 1. Install

Requires Python 3.12 and CUDA 12.8 toolchain on a GPU host (or CUDA
stubs on a CPU-only host). One editable install builds vLLM and
registers the plugin:

```bash
git clone --branch release/open-v0.1 <repo-url> vllm-emulator
cd vllm-emulator
python3 -m venv .venv && source .venv/bin/activate
pip install --upgrade pip wheel setuptools
VLLM_VERSION_OVERRIDE=0.18.1 \
VLLM_USE_PRECOMPILED=1 \
pip install -e . \
  --extra-index-url https://download.pytorch.org/whl/cu128
```

(`VLLM_VERSION_OVERRIDE=0.18.1` is required when installing from a git
checkout that doesn't reach a vLLM version tag in its ancestry —
vLLM's `setup.py` calls setuptools-scm directly and can't otherwise
infer the version.)

The `pip install -e .` registers the `vllm.platform_plugins` entry point
`emulator -> vllm_emulator.platform:emulator_platform_plugin`. With
`VLLM_EMULATOR_ENABLE_ORACLE` unset, the plugin is a no-op and vLLM
runs as usual.

If `VLLM_USE_PRECOMPILED=1` hits an ABI mismatch on a cloud host, the
four vLLM CUDA `.so` files (`vllm/_C.abi3.so`, `vllm/_moe_C.abi3.so`,
`vllm/cumem_allocator.abi3.so`,
`vllm/vllm_flash_attn/_vllm_fa2_C.abi3.so`) can be copied byte-for-byte
from a known-good install on a compatible host into your venv's
`site-packages/vllm/` to bypass the runtime build.

## 2. Prepare the dataset

The ShareGPT prompts/responses used by every cell are reproducible


`tools/download_filter_sharegpt.py` reads from
`anon8231489123/ShareGPT_Vicuna_unfiltered` on Hugging Face Hub.

## 3. Run vLLM with the emulator

The plugin is selected by env var on the same `vllm serve` line you'd
use without it:

```bash
# Real vLLM (no emulator):
vllm serve Qwen/Qwen3-8B \
  --port 8000 --max-model-len 4096 --gpu-memory-utilization 0.85

# GhostServe emulator (no GPU forward pass; uses profile pack from Phase A):
VLLM_EMULATOR_ENABLE_ORACLE=1 \
VLLM_EMULATOR_PROFILE_PACK=results/RTX-8000-adaptive-<CELL_TAG>/serving-full.json \
VLLM_EMULATOR_MODE=realtime \
CUDA_VISIBLE_DEVICES="" \
vllm serve Qwen/Qwen3-8B \
  --port 8001 --max-model-len 4096 --gpu-memory-utilization 0.85
```

(The profile pack is generated by `tools/adaptive_profile_capture.sh`
in §4 below; this repo ships only the scripts, no pre-built packs.)

Both servers expose vLLM's standard OpenAI-compatible HTTP API at the
chosen port.

## 4. Reproduce paper Table 1

Each cell runs the same 3-stage orchestrator with cell-specific config:

| Cell | Hardware | Model | Extra config |
| --- | --- | --- | --- |
| **M-Q8** (main)            | RTX 8000 | Qwen/Qwen3-8B  | (default) |
| **M-Q14** (model-scale up) | RTX 8000 | Qwen/Qwen3-14B | (default) |
| **A40-Q8** (hardware swap) | A40      | Qwen/Qwen3-8B  | (default) |
| **M-Q8-Burst** (workload)  | RTX 8000 | Qwen/Qwen3-8B  | `BENCH_BURSTINESS=0.25` |
| **A40-L8** (model-family)  | A40      | meta-llama/Llama-3.1-8B | `BENCH_IGNORE_EOS=1` |
| **A40-Q4** (model-scale down) | A40   | Qwen/Qwen3-4B  | (default) |

Drive a single cell with the deterministic-KV orchestrator:

```bash
# Example: M-Q8 cell on RTX 8000
CELL_TAG=mq8-main \
BENCH_MODEL=Qwen/Qwen3-8B \
HW_PREFIX=RTX-8000 \
STUB_DIR=$HOME/cuda_stubs \
bash tools/_orch_3stage_detkv.sh
```

The orchestrator:
1. **Phase A** captures the profile pack with
   `tools/adaptive_profile_capture.sh` (real GPU, no KV override).
2. **Phase B** picks the lowest observed `GPU KV cache size` from
   server logs via `tools/_calibrate_kv_min.py` and emits
   `--num-gpu-blocks-override=N`.
3. **Phase C** runs the real bench AND the emu validate at the SAME
   pinned KV pool, via `tools/run_one_full_sharegpt_cell.sh`.

Per-cell flags:

```bash
# M-Q14 (RTX 8000, Qwen3-14B)
CELL_TAG=mq14-modelscale-up BENCH_MODEL=Qwen/Qwen3-14B \
HW_PREFIX=RTX-8000 \
bash tools/_orch_3stage_detkv.sh

# A40-Q8 (A40, Qwen3-8B, hardware swap)
CELL_TAG=a40q8-hardware-swap BENCH_MODEL=Qwen/Qwen3-8B \
HW_PREFIX=A40 \
bash tools/_orch_3stage_detkv.sh

# M-Q8-Burst (RTX 8000, Qwen3-8B, gamma=0.25)
CELL_TAG=mq8-burst-gamma025 BENCH_MODEL=Qwen/Qwen3-8B \
HW_PREFIX=RTX-8000 BENCH_BURSTINESS=0.25 \
bash tools/_orch_3stage_detkv.sh

# A40-L8 (A40, Llama-3.1-8B, --ignore-eos)
CELL_TAG=a40l8-llama-igeos BENCH_MODEL=meta-llama/Llama-3.1-8B \
HW_PREFIX=A40 BENCH_IGNORE_EOS=1 \
bash tools/_orch_3stage_detkv.sh

# A40-Q4 (A40, Qwen3-4B)
CELL_TAG=a40q4-modelscale-down BENCH_MODEL=Qwen/Qwen3-4B HW_PREFIX=A40 \
bash tools/_orch_3stage_detkv.sh
```

Each cell writes:

```
results/<CELL_TAG>/real_r{2,4,8,16,32}.json   # vLLM bench output
                  emu_r{2,4,8,16,32}.json    # GhostServe bench output
                  per_rate_deltas.csv         # %-error per metric per rate
results/<HW_PREFIX>-adaptive-<CELL_TAG>/
                  serving-full.json           # the profile pack
                  per_rate_traces/            # raw step-cycle traces
```

Generate Table 1 from completed cells:

```bash
python tools/_paper_pack_audit.py results/
```

### What "reproduces the paper" means

Each cell's `per_rate_deltas.csv` reports the percentage difference
between real and emulated bench at each rate, in the order
`rate, ttft_mean_pct, tpot_mean_pct, itl_mean_pct, e2e_mean_pct, tps_pct`.
The five metrics are TTFT, TPOT, ITL, E2E latency, and TPS
(tokens per second).

For reference, the published v1 Table 1 max-abs deltas on the same
hardware/model (your numbers will move within capture-to-capture
variance):

| Cell | TTFT | TPOT | ITL | E2E | TPS |
| --- | ---: | ---: | ---: | ---: | ---: |
| **M-Q8**       | 9.81% | 0.85% | 0.80% | 2.02% | 0.78% |
| **M-Q14**      | 9.10% | 1.37% | 1.33% | 1.51% | 1.10% |
| **A40-Q8**     | 9.22% | 1.52% | 1.26% | 3.72% | 1.25% |
| **M-Q8-Burst** | 10.41% | 4.75% | 4.69% | 4.77% | 1.88% |
| **A40-L8**     | 9.32% | 1.98% | 1.92% | 3.48% | 1.76% |
| **A40-Q4**     | 7.78% | 3.10% | 3.01% | 5.22% | 1.50% |

### Single-cell quick reproduce (M-Q8)

The shortest end-to-end run that demonstrates a paper-quality cell:

```bash
# 1. Build the dataset (downloads ShareGPT V3 from HuggingFace, ~5 min)
python tools/download_filter_sharegpt.py

# 2. Build CUDA stubs once (only needed for the emu side)
mkdir -p $HOME/cuda_stubs && cd $HOME/cuda_stubs
ln -sf /usr/local/cuda/targets/x86_64-linux/lib/stubs/libcuda.so libcuda.so.1
ln -sf /usr/local/cuda/lib64/libcudart.so.12 .
cd -

# 3. Run the M-Q8 cell (~4-5 hours wall on RTX 8000):
#      Phase A (profile capture)  ~3 hours
#      Phase B (KV calibrate)     instant
#      Phase C (real × 5 rates)   ~50 min
#      Phase C (emu  × 5 rates)   ~30 min
CELL_TAG=mq8-reproduce \
BENCH_MODEL=Qwen/Qwen3-8B \
HW_PREFIX=RTX-8000 \
STUB_DIR=$HOME/cuda_stubs \
bash tools/_orch_3stage_detkv.sh

# 4. Inspect deltas
cat results/mq8-reproduce/per_rate_deltas.csv
```

Compare your `per_rate_deltas.csv` against the published M-Q8 row
above. The five columns are TTFT, TPOT, ITL, E2E, TPS percentage
deltas. Single-rate spikes at the prefill→saturation transition
(typically r=8 on Qwen3-8B/RTX 8000) can occur from capture-to-capture
variance and are characteristic of profile-driven emulation; rerunning
Phase A on a quiet host usually pulls them back in.

## 5. Environment variables

| Var | Purpose |
| --- | --- |
| `VLLM_EMULATOR_ENABLE_ORACLE`     | `1` activates the plugin; unset = pass-through |
| `VLLM_EMULATOR_PROFILE_PACK`      | path to `serving-full.json` |
| `VLLM_EMULATOR_MODE`              | `realtime` (sleep for predicted latency) or `accelerated` (no sleep) |
| `VLLM_EMULATOR_MOCK_CUDA`         | `1` activates `torch.cuda` stubs (CPU-only hosts) |

---

## 6. Paper data

This release ships **only the code that reproduces the paper**. The
captured profile packs, real/emu bench JSONs, raw step-cycle traces,
and host-specific pip-freezes that produced the v1 Table 1 are not
included in the repo (they are workload-specific outputs of the scripts
above, not source). Each `tools/_orch_3stage_detkv.sh` invocation
regenerates them deterministically into `results/<CELL_TAG>/` and
`results/<HW_PREFIX>-adaptive-<CELL_TAG>/`.
